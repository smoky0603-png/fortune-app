# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Japanese-language tarot reading web app ("タロット占い"). Users pick a theme, optionally type a question, draw cards, and receive an AI-generated reading. Three of four themes are paid (Stripe Checkout); the free theme and any AI failure fall back to a locally-generated reading.

## Commands

```
npm install
npm run dev       # vite dev server (serverless /api functions are proxied locally, see below)
npm run build     # vite build -> dist/
npm run preview   # preview the production build
```

There is no test suite, linter, or type checker configured in this repo (no test framework, ESLint config, or TS present). Don't invent commands for these — `npm run dev`/`build`/`preview` are the only scripts.

### Environment variables (`.env`, gitignored)

```
ANTHROPIC_API_KEY=sk-ant-xxxx
STRIPE_SECRET_KEY=sk_test_xxxx   # or sk_live_xxxx
```

`ANTHROPIC_API_KEY` is optional — if unset (or the API call fails/returns an incomplete response), the app silently falls back to `buildLocalReading` so a result is always shown. `STRIPE_SECRET_KEY` is required for any paid theme to reach checkout.

## Architecture

This is a Vite + React SPA (no router library — view switching is done by hand) backed by Vercel serverless functions in `api/`. There is no build-time API key exposure: all secret-bearing calls happen server-side in `api/*.js`, never from the client.

### Request flow for a reading

1. `src/App.jsx` holds all view state (`phase`: `form` → `redirecting`/`loading` → `report`) and the theme catalog (`THEMES`, hardcoded with `id`, `positions` array, and `price` in yen — `0` for the free daily theme).
2. Free theme: `handleDraw` calls `runReading` directly. Paid theme: `handleDraw` POSTs to `/api/create-checkout-session` and redirects to the returned Stripe URL.
3. `runReading` draws cards via `drawCards()` (`src/tarotDeck.js`), builds a Japanese prompt embedding each position's card/orientation/meaning, and POSTs it to `/api/generate-reading`, which proxies to the Anthropic Messages API using the server-side key.
4. The AI's response text is parsed back out by regex-matching `【position label】...` sections (the prompt explicitly asks the model to use this format) into `perPosition[]` + `overall`. If parsing fails, errors, or any section is empty, it falls back to `buildLocalReading()` (`src/localReading.js`), which synthesizes a reading procedurally from card meanings — no network call.
5. After Stripe redirect back to `/?session_id=...`, a `useEffect` in `App.jsx` calls `/api/verify-checkout-session` to confirm `payment_status === "paid"` and pulls `themeId`/`question` back out of the Checkout session's `metadata` (since state was lost on redirect), then runs the reading automatically.

### `api/` (Vercel serverless functions, one file = one route)

- `generate-reading.js` — thin proxy to `https://api.anthropic.com/v1/messages`, forwards `req.body` as-is, attaches `ANTHROPIC_API_KEY`.
- `create-checkout-session.js` — validates `themeId` against the server-side `PRICES` map (love/work=¥500, general=¥1000 — **this is the source of truth for pricing, not `App.jsx`'s `THEMES`**), creates a Stripe Checkout session, stores `themeId`/`question` in session `metadata` (question truncated to 480 chars), redirects to `/` with `session_id`.
- `verify-checkout-session.js` — retrieves the Stripe session by `session_id` and returns whether it's paid plus the stashed `themeId`/`question`.

When changing prices or adding a paid theme, update `PRICES` in `create-checkout-session.js` AND the matching `price`/`positions` entry in `THEMES` in `App.jsx` — they are not derived from each other.

### Local dev API proxying

`vite.config.js` defines a custom Vite plugin (`tarotApiDevProxy`) that intercepts `POST /api/generate-reading` during `npm run dev` and calls the Anthropic API directly, since `vite` alone doesn't execute the `api/` serverless functions (that normally requires `vercel dev`). `create-checkout-session` and `verify-checkout-session` are **not** proxied this way — they only work under `vercel dev` or in production on Vercel.

### Card data (`src/tarotDeck.js`)

- `TAROT_DECK` = 22 major arcana (hardcoded array with upright/reversed meanings + a longer `detailUpright`/`detailReversed` sentence) + 56 minor arcana (generated by crossing `SUITS` × `RANKS`).
- `drawCards(count)` shuffles and slices the deck, assigning a random `isReversed` per card independently (so duplicate suits/ranks across positions are possible but duplicate cards within one draw are not, since slicing happens after shuffling without replacement).
- `meaningOf(card)` / `detailOf(card)` pick the upright or reversed text based on `card.isReversed`; `detailOf` only exists for major arcana (returns `null` for minor).

### Rendering

- All CSS is inline template strings injected via `<style>{STYLE}</style>` per-component (in `App.jsx` and `legal/LegalPages.jsx`) — there are no `.css` files or CSS modules. Keep new styling in this same pattern rather than introducing a separate stylesheet approach.
- `src/CardArt.jsx` renders hand-drawn SVG icons per suit (`SuitIcon`) and per major-arcana card (`MAJOR_ICONS`, keyed by card number 0–21) — no external icon library or images.
- `src/legal/LegalPages.jsx` exports `TermsOfService`, `PrivacyPolicy`, `Tokushoho` (specified commercial transactions act disclosure, required for Japanese e-commerce). Routing between the main app and these pages is via `window.location.hash` (`#/terms`, `#/privacy`, `#/tokushoho`), checked in `App.jsx`'s `LEGAL_PAGES` map — there is no React Router.

## Conventions

- All UI copy, prompts sent to the AI, and code comments explaining non-obvious business logic are in Japanese; this is a Japan-market product (JPY pricing, Tokushoho disclosure) and that should be preserved in new code/UI text.
- No JSX/CSS framework (no Tailwind, no styled-components) — plain inline `<style>` strings with hand-rolled class names, as above.
- Serverless functions in `api/` all set permissive CORS headers and handle `OPTIONS` manually — follow the same shape for new endpoints.
